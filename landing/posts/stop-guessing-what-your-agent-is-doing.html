Stop guessing what your agent is doing

2026-11-22 · notes from building LaneConductor

Most of the time, an agent does its work and you find out what it did at the end. Sometimes you can't even do a post-mortem, because nothing recorded where the effort went. I wanted to stop guessing, so I made the work visible at three moments.

Before: the plan says what it will do. In LaneConductor a piece of work is a folder of plain files, and plan.md is a list of phases with checkboxes. Before any code is written you can read what the agent is about to do, change it, and see which steps are marked as waiting for a person.

During: the boxes show what it is doing now. The agent ticks a box when a task is done and its check passed. Because the plan lives in git and a board reads it, you can see which phase is running, what is done, what failed its test, and what is parked waiting for you. You don't need to scroll a chat to know where it is.

After: the numbers show how it went. A SQL database has EXPLAIN, which shows where a query spends its time. Agent work had the same blind spot, so I added the equivalent. Every Claude Code session already keeps a record of token counts and timestamps, and every track keeps ticks and dated lines in git. A small script joins them and gives the plan with costs, per lane and per phase: time spent working versus waiting for a person, tokens (output, fresh input, cache), tool calls and how much a sub-agent did. The agent doesn't write these numbers, because it can't read a clock or its own meter. They are measured from outside, and only counts, times and tool names are read, never what was said.

What it showed on one small track (a skill pack: plan, implement, review, 20 minutes, 3 of them waiting on me): 79 model responses wrote 43,600 tokens and read 15.8 million tokens from cache, about 360 times what was written. On a bigger track it was 540 times. Every reply re-reads the whole conversation so far, about 200,000 tokens per reply on the small track and 266,000 on the bigger one. The first reply of a lane already carried 646,000 to 958,000 tokens of history, because it ran in one long session.

I had a theory: the instruction text each lane carries (about 27 KB) must be the cost. It was about 3 percent of one reply's context. The real cost is the length of the session doing the work. A sub-agent in its own worktree starts at a median of 35,000 to 57,000 tokens, against 95,000 to 770,000 for the long session. So I changed the default: lane work goes to a sub-agent unless you say otherwise.

I would not have found this without the three views. The plan told me what was supposed to happen, the ticks told me it did, and only the numbers told me what it cost.

Limits: this is one repository and a few tracks. It counts tokens, not money. Attributing messages to a track is by time window, so overlapping work can share numbers, and about half of the tracks I looked at never recorded when a lane started, so their times are only inferred. Read these as relative numbers.

LaneConductor is a personal project and a pattern being explored. Plans, tracks and the board are plain files in git, and the plugin is open source. Read how it works or see the docs.
