A Claude plugin, plain files in git

Build your project.
Ask what's next.

LaneConductor takes you through a project the way good teams work: a spec, a plan, test cases, a review and a quality gate, all kept as plain files in your repository. Type /laneconductor:next and Claude names the one step to take, explains it, and does it with you. No database, no background service.

$ claude plugin marketplace add meller/laneconductor claude plugin install laneconductor@laneconductor

Then, in Claude, type /laneconductor:next. Every command comes with the base plugin, and what's next is built from your project's own files.

For Claude Code or Cowork, with Node.js 20 or newer. Add --scope local to install for one project, then run /reload-plugins.

$ claude plugin install laneconductor-board@laneconductor claude plugin install laneconductor-parallel@laneconductor

The full version, two extras: the board, a private view of every track inside Claude where each card shows its next step, and parallel, sub-agents that work several tracks side by side, each in its own git worktree.

How it works

Install it. Ask Claude. See the board.

Set a project up once, then work each track through its lanes by asking Claude or by using a slash command.

Once per project
01 — INSTALL
Add the plugin

Two commands in a terminal. Then run /reload-plugins in your session and check that /mcp lists plugin:laneconductor:lc.

claude plugin marketplace add meller/laneconductor
claude plugin install laneconductor@laneconductor
02 — SET UP
Prepare the repository

Claude tells you what it will create before it writes anything, then sets up the conductor/ folder.

/laneconductor:setup
03 — FIRST TRACK
Describe the work

Say what and why. Claude checks for a similar track first, then creates the track folder.

/laneconductor:new <title: what and why>
For each track
01 — PLAN
Claude writes the spec and plan

They land in the track folder as Markdown. Read them, edit them, comment on them. Claude follows what you change.

/laneconductor:plan 12
02 — BUILD
Implement, review, gate, merge

Each lane has a command. Claude recommends a track-runner subagent in its own worktree for the work, and nothing starts until you say yes.

/laneconductor:implement 12
03 — SEE
Ask for the board

Every track by lane, as a private artifact. It is a snapshot: it changes when you ask Claude to update it.

/laneconductor:board

Where the plan lives

Without

You describe the feature in chat and Claude answers with a plan. The plan is a message in the conversation.

When the session ends, so does the plan. The next session starts cold: you explain again what was decided and what is done.

With

A track folder appears in the repository. Claude writes the spec, the plan and the tests as files, and you read and fix them before any code exists. A later session, or another person, opens the track and sees where it stands: the lane, the phase and which tasks are ticked.

  • test.md test cases
  • conversation.md comments, kept on your machine

Advice at each lane

Without

Whether Claude brainstorms first or writes the test first depends on what you remember to ask for.

With

Each lane has a guide that Claude reads before it works there. The plan lane picks up a brainstorm thread from the track's conversation. The implement lane recommends writing each test first, because test.md is written for it. Each guide also names the skills that help in that lane, such as brainstorming before the plan or test-driven development while building; if one is installed Claude uses it, and if not it says so. You can add your own per lane. The guides are advice, not orders: when Claude decides against one, it records why.

Who does the work

Without

The work happens in the one chat you are talking to.

With

For each track, Claude recommends a track-runner sub-agent that works the plan in its own git worktree. Nothing starts until you say yes. Several tracks can run side by side, one sub-agent each, and the main session stays free.

Checking the work

Without

Claude writes the code. Nothing compares it with a written spec, and your project's checks run only if you ask for them.

With

Two lanes come after implement. In review, the code is checked against the spec. In the quality gate, your project's own checks run: the commands listed in conductor/quality-gate.md, such as tests and lint. Then the track moves to done.

The overview

Without

No overview of what is in progress, apart from what you remember.

With

The board is a private dashboard generated from the track files: every track by lane, with its progress and phase. Claude publishes it as an artifact with your approval. It is a snapshot, so it changes when you ask Claude to update it. Every document is scanned for secrets and personal data before it goes on the board, and opening a track shows its plan, spec and tests.

Two sessions at once

Without

Two sessions editing the same file: the last save wins.

With

Every write names the version you last read. If someone changed the file since, the write is refused and nothing is overwritten. Each write is one git commit. This is what a second session saw when it tried to change a track the first session had already changed:

update_track, second session
ERROR CONFLICT: 1 item changed since your base: marker Progress Hint: Someone else edited first. Re-read with get_track, merge their change with yours, and retry with the new base. The earlier edit is untouched.

It is the same Claude either way. What changes is the agreement before the code, the check afterwards, the record in git, and shared state that two sessions cannot silently overwrite.

Architecture

Files in git.
Claude plus a connector.

Tracks are Markdown files in your repository. Claude reads and writes them through a small local connector. There is no database and no daemon; the older tier that had both is optional and parked.

Files, not a database

The track files in conductor/tracks/ are the source of truth, and git keeps their history. They are plain text, so you can read and edit them yourself.

One writer, checked writes

A write must carry the version you last read. If the file changed since, the connector refuses it with a CONFLICT, and you merge and retry. Nothing is silently overwritten.

A state branch per repo

The connector writes on connector.state_branch if you set it, otherwise the repo's default branch, otherwise main or master. It refuses to write on any other branch and asks before any push.

Why this way

Plain files.
Nothing to run.

Keeping plans as files in git, and letting Claude manage them, removes the parts of a tracker that you would otherwise have to host and keep in sync.

Nothing to host

No database, no daemon, no worker. If the connector's server fails to start, the commands fall back to editing the track files directly.

Stays with your repo

The connector makes no network requests of its own. The advice log it keeps holds tool names, timings and sizes, never file contents or prompts, and conversation.md is gitignored and stays on your machine.

Human-first truth

Markdown is the source of truth. If you edit a plan, Claude follows it. If Claude hits a blocker, it writes a comment. All of it has git history.

Lanes with a gate

Plan, implement, review, quality gate, merge. The quality gate runs your own tests, lint and build, and the skill asks before any push or merge.

A board you control

The board is a private artifact that Claude refreshes when you ask. Documents are scanned first, and sharing the board shares those documents.

Honest limits

No remote connector for chat and mobile, and no listing in Anthropic's plugin directory yet. We say so here so you do not find out later.

Features

Everything you need.
Nothing you don't.

📋
The board

Every track by lane, as a private Claude artifact. Click a track to open its Overview, Plan, Spec and Tests. It is a snapshot that changes when you ask Claude to update it.

/laneconductor:board
⚙️
Slash commands for every step

Type /laneconductor: to list them all: plan, implement, review, quality-gate, merge, run, new, new-project, bug, feature, status, move, comment, board, workflow, help and more. Most take a track number or a title; setup and deploy run only when you name them.

/laneconductor:<name>
🤖
A subagent per track

track-runner works one track through one lane in its own git worktree, so tracks do not collide. It is recommended, and starts only when you say yes.

worktree per track
🔍
Plan review

plan-reviewer reads a track's spec and plan and reports gaps. It is read-only and changes nothing.

/laneconductor:review-plan
🛡️
Safe writes

Writes are checked against the version you last read, committed one change at a time, and refused on any branch other than the state branch.

CONFLICT checks
🔐
Privacy scan

Before a document goes on the board it is scanned. A file with secrets, email addresses or phone numbers is withheld whole and named by track and file. conversation.md is not included unless you turn it on.

board privacy
🏗️
Programmable workflows

The lanes and where each one goes next are set in a file you own, and you can change them with /laneconductor:workflow.

workflow.json
✅
Quality Gate lane

Tests, lint and build run before a track is marked done. You set the checks per project in a checklist file.

quality-gate.md
📚
Skills for each lane

Each lane guide names the skills that help there, such as brainstorming before a plan or test-driven development while building. They are suggestions: if a skill is installed Claude uses it, if not it says so. You can list your own per lane in workflow.json.
