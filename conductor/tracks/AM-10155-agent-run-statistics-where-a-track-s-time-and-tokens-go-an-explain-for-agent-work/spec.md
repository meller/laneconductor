# Spec: agent run statistics (AM-10155)

## Problem Statement
An agent's work on a track is invisible in cost: time, tokens, tool calls. The plan shows what was done, not what it cost. Like an SQL EXPLAIN shows where a query spends its time, a track needs a plan-with-costs, so inefficiency in how we use the code and the tracks data becomes visible and can be fixed.

## Why measure from outside
An agent cannot read a clock or its own token meter, so asking it to write timings into the plan would produce invented numbers. The measurements come from records the tools already keep.

## Sources (read only)
- Session transcripts under the Claude config folder (`projects/<project>/<session>.jsonl`, sub-agent runs included): per-message token counts (output, input, cache creation, cache read), timestamps, tool names and durations, the skill or plugin that was running, the working directory and branch.
- The track files and git: plan.md ticks (commit times), dated lines in history.md, lane claims, commit times.

## Requirements
- REQ-1 A script `lc-explain.mjs` in the board add-on (`node lc-explain.mjs --repo . --track <N>`) prints the statistics and writes `explain.md` into the track folder. It is read-only toward the transcripts and the repository.
- REQ-2 Boundaries: a lane run starts at its claim (the Lane marker change) and ends at its completion line; phases inside implement are bounded by the plan.md tick commits. Transcript messages are attributed to a track by the time window and the working directory or branch, not by reading their content.
- REQ-3 Per lane and per phase: wall-clock split into active time and waiting on a human (human time from the `(HUMAN)` plan markers and the waiting status, see D4); tokens as output, fresh input, cache creation and cache reads, shown separately (cache reads dominate and cost little); tool calls by kind; the slowest steps; the share done by sub-agents; files read more than once, as a count of repeats (see REQ-4).
- REQ-4 Privacy: only numbers, timestamps and tool names are read or written. No prompt, message or file content, no secret. A test feeds a transcript whose content holds a token and an email and asserts neither reaches the output.
- REQ-5 `explain.md` is generated and overwritten on each run, never edited by hand, and says when it was generated and from which sessions. It is the stored record, because transcripts are local and can be cleaned up.
- REQ-6 The board shows it as an "Agent run" tab next to the track's other documents (overview, plan, spec, tests), with a per-phase table. The board's privacy scan applies to it like any document.
- REQ-7 The first version changes no base plugin text, so there is no new base version for the directory review. A later phase may have the lanes run the script at completion and add a short suffix to the completion line in history.md; that is base text and its own track.
- REQ-8 Use it: run it on finished tracks (10154 first), record what it shows in this spec, and name the biggest inefficiencies. One hypothesis to test: each lane command carries about 27 KB of reference text, so every lane run pays for it before any work starts.
- REQ-9 The post "Pick Your Agent's Brain" (draft under track 10112) uses real output of this script, and every number in it is checked.

## Probe findings (2026-11-21, plan lane, read-only, on this repository's own session transcript in the desktop app)
- Each assistant message carries a usage record: input, output, cache creation and cache read tokens, plus a thinking-token count. Messages carry a timestamp, the working directory and the git branch.
- Sub-agent runs are separate transcripts in `<session>/subagents/agent-<id>.jsonl`, flagged as side chains, with the parent's session id and their own usage records. So their tokens can be added to the parent's window.
- One session file can span months (this one runs from 2026-09-07 to 2026-11-21, across resumes and compactions) and many tracks, so a lane run must be cut out by its time window, never by session.
- A session that works in a worktree shows the worktree path as its working directory and the track branch (for example `.worktrees/10099`); sessions started inside a worktree get their own project folder.
- A tool's duration is rarely recorded: only 62 tool results carried a duration field against about 13,700 assistant messages, so durations must be computed from the timestamps of the call and of its result. That includes any wait for a permission answer, so it is approximate.
- Not yet checked: the same layout in a plain CLI session (the probe was the desktop app); Task 1 of the plan repeats the probe there.

## The insight comes first (owner, 2026-11-22)
- D13 The Agent run tab opens with an insight, not with notes and a 13-column table. `explain.md` starts, right after its title, with a section `## Insight`; the generated-by note, the sources, the approximation note and the tables follow. The insight is made by the script from the numbers with fixed rules (no model, repeatable, free): it is labelled as rule-based observations, not an opinion of a model. Content: (1) time: wall, agent and human time, and a line when most of it was waiting for a person; (2) work: replies, tokens written, tokens read from cache, the ratio and the average per reply; (3) context: the first reply of the lane runs in the main session against where sub-agents started, when known; (4) sub-agents: their share of replies and output, or that none were used; (5) the biggest lane or phase by time and by tokens; (6) "What to look at", only the rules that fire: a long main session (first-reply context of 400,000 tokens or more and a sub-agent share under 30 percent) suggests a sub-agent or a fresh session; lane runs with no claim commit or never closed are upper bounds, so claim the lane when starting it; files read more than once; gaps of more than 30 minutes; a slowest step of 5 minutes or more (a permission wait is included); when none fires, "Nothing unusual". Every number is traceable to the tables below it. A short "Discuss" is still available on the card for a conversation with Claude.
- D14 `statistics.md` starts with an `## Insight` of its own across tracks: how many tracks have statistics, the track with the highest cache-read ratio and the one with the most human waiting, the total tokens written and read, and how many finished tracks have no statistics yet.

## Recommendations for the next run (owner, 2026-11-22)
The owner's question as a user: "how could I improve my run?" The agent run report should say what to do differently next time (a different model, a sub-agent, a different effort, where the time went), so AI usage can be optimized. Tokens only (D2): no dollars and no promise of savings; the rules are suggestions with their evidence.

Probe (2026-11-22, on this repository's own transcripts, numbers only): every assistant reply records the model that answered (`message.model`); the usage record carries thinking tokens (`output_tokens_details.thinking_tokens`; 8,189 of the 43,599 output tokens, 19 percent, in the 10154 window); every transcript line carries the effort level of the turn (`effort`, `perTurnEffort`, "high" for all 139 lines of that window); sub-agent transcripts carry the same fields, and across this session they used a mix of models (mostly one, a few on a larger and a few on a smaller). So model mix, thinking share and effort level are measurable without reading any content.

- D15 `explain.md` gets a section `## Recommendations` right after `## Insight`: actions for the next run, each with its evidence number, from fixed rules; the Insight keeps the observations ("What to look at"), the Recommendations say what to do. When no rule fires: "No change suggested".
- D16 The rules (thresholds are constants, tuned on more tracks): (1) where to run: a lane run that began with 400,000 tokens of context or more and had under 30 percent of its replies from sub-agents: run it in a sub-agent or a fresh session (a sub-agent starts near 50,000); (2) which model: a phase whose tool calls are at least 80 percent shell, read or file edits and whose output per reply is small, and that ran on the largest model tier: a smaller model for that phase's sub-agent; and a phase with high output, much thinking or many failed steps that ran on a small model: keep or use a larger one (the tier is read from the model id: opus above sonnet above haiku, stated as a heuristic); (3) effort: thinking tokens of 30 percent or more of the output in a mechanical phase, or effort "high" on every turn of a mechanical phase: a lower effort; (4) waiting: a slowest step of 5 minutes or more: allow that command so it does not wait for a permission (a permission wait is included in the time, so this is a suggestion to check); (5) claims: lane runs with no claim commit: claim the lane when starting it; (6) a suggested setup for the next run: one line per lane with where to run it, the model tier and the effort.
- D17 A per-phase "Path": the tool kinds in the order they were used, run-length encoded and cut to the first 8 segments (for example "Read x12, Bash x26, Write x2"), so the owner sees what the agent went through; times are the phase's own.
- D18 `statistics.md` gets recommendations across tracks: the model mix of all replies, the share of lane runs with no claim commit, and the tracks where a recommendation fired most often. The board shows both as the first sections of their tabs after the insight.
- Out of scope for this phase: changing any model or effort setting automatically, dollar costs, and a model judging quality of the work.

## Phase 9: a short plan first, and recommendations across tracks (owner, 2026-11-22)
The owner's feedback on the finished explain: too much detail, "noise" for a lot of people. It should read like an SQL EXPLAIN: a small table of steps, a few lines, the expensive step visible, so the reader sees where to improve. And an "Agent recommendations" button at the top of the board that analyses roughly the last 10 tracks and recommends how to optimize runs (for the owner improving LaneConductor, and for users).

- D19 The top of the Agent run tab is a short plan, built from numbers already computed: one table with a row per lane run (or phase when the lane runs are one) with Step, Where (main session or sub-agent), Time (human time in brackets), Written (output tokens) and Context at start (tokens); the most expensive step is marked in a last column ("expensive", chosen by the largest context at start, ties by time); at most three lines below it, each one a fix with its number and where to change it. Everything that exists today (Insight, Recommendations, Path, Model use, lane and phase tables) stays, folded under "Details". The same short plan is the first thing in `explain.md` (before `## Insight`), so a reader of the file and of the board sees the same.
- D20 The short plan keeps the rules of D2 and D4: tokens only, an approximation note under the table, numbers and tool names only (REQ-4). No new measurement: it is a view over the numbers of phases 2 to 8.
- D21 The board gets an "Agent recommendations" button at the top (next to Project and What next). It opens a drawer built from the last 10 finished or running tracks that have an `explain.md` (newest first; the number is the constant `RECOMMEND_WINDOW`, so it can change). The drawer shows at most three actions, ranked by how many of those tracks each applies to, each with one number (for example "7 of 10 tracks planned with over 400,000 tokens of history") and a Copy button that copies one plain sentence for the agent to apply. A sentence under the list names the tracks it looked at.
- D22 (the per-action minimum of 3 tracks is replaced by the levels of D28) Ranking rules: an action is a D16 rule that fired in at least 3 of the tracks in the window (constant `MIN_TRACKS`); ranked by tracks affected, then by the tokens involved. Fewer than 3 tracks with an explain: say "Not enough tracks with statistics yet (N of 3)" and nothing else. No rule over the threshold: "No change suggested across the last N tracks."
- D23 Where the data comes from: the board already loads each track's documents, so the drawer reads the `explain.md` sections it has. The script `lc-explain.mjs` writes one machine-readable block per track (a fenced `json` block named `recommend-facts`: the rule ids that fired with their numbers, no content) so the board does not parse prose; tracks whose explain.md has no such block count as "not measured".
- D24 Audience: the owner improves the lane texts and defaults from the cross-track view; a user gets three plain actions. A project that does not work through tracks gets nothing here (the explain needs lanes and phases); the drawer says so in one line when no track has statistics.
- Out of scope for this phase: changing any setting automatically, dollars, a model judging quality, a recommendation from fewer than 3 tracks.

## Phase 10: discuss the recommendations, and one window is not credited to many tracks (owner, 2026-11-22)
- D25 (owner) The Statistics tab (the Project drawer's `statistics` tab) gets a button **Discuss actions from stats** at the top. Like the board's other Discuss buttons it only copies a plain prompt (no model call, nothing is sent): read `conductor/statistics.md` and its Recommendations section, say which of the recommended actions apply to this project, and discuss each one with the owner before changing anything; never apply a change without a yes to that action. Numbers and paths only in the prompt (REQ-4). Reason: the recommendations are only useful when the owner and the agent talk them through; a button that applies them would break the rule that nothing changes without a yes.
- D26 (owner; evidence from running `lc-explain` on 12 more tracks) When several tracks sit in the same lane at the same time and the lane was never claimed with a running commit (for example quality-gate from 2026-11-18 14:40 to 2026-11-22 14:40 on AM-10130, 10133, 10141, 10143, 10144, 10145, shown as `no claim commit` or with a 92h32m human wait), every one of them is credited with all the replies of that window (about 3,400 to 4,700 responses each, an identical human wait), so per-track tokens and the cross-track totals count the same replies several times. Rule: the replies of a lane window are attributed to a track only when the window is a claimed running window (the lane status became `running` in it), or when no other track has an overlapping window in the same lane of the same repository. Otherwise the lane run keeps its time but its tokens read `not measured (shared window)`, are left out of the track's totals, of `statistics.md` totals and of the recommendation rules (the claim rule stays: claiming the lane is the fix). Refinement made while building it (the owner's condition that AM-10154 stays unchanged): AM-10154's implement and review windows overlap only the long waiting windows of AM-10150 and AM-10148 (human waits). A window that never ran is shared when another track's window in the same lane overlaps it, with one difference by kind: a waiting-only window (human wait, no agent work of its own by D4) is shared by any overlapping window of that lane; an unclaimed window (inferred agent time) is shared only when the other window is agent time too (unclaimed or running). So of two overlapping windows exactly one keeps the replies (the unclaimed one beside a waiting-only one), and no reply is credited twice. Known limit: the working directory cannot be compared without the transcripts, so overlap is judged on the lane windows only. Reason: a token total that counts the same replies four to six times misleads the very decisions the explain is for.
- D27 (owner, 2026-11-24, found by using it) One set of recommendations. `conductor/statistics.md` gets its `## Recommendations` from the same function as the board's Agent recommendations drawer (`rankFromExplains` in `explain-rank.mjs`): the same at most three ranked actions over the same last 10 tracks, each with its count, in plain lines; the not-enough and quiet states use the drawer's messages. The descriptive lines that were there (model mix of all replies, lane runs with no claim commit, tracks where most rules fired, and the no-model-data and no-recommendations-yet notes) move to the `## Insight` of statistics.md as bullet lines, wording unchanged. The track number of each explain.md is read from its folder name (`AM-10154-...` and `10154-...` both give 10154). The section title stays `## Recommendations` (the Discuss actions from stats prompt reads it by name). Nothing about the single-track report changes. Numbers only, no dollars, no prompt or message content. Reason: two different outputs for the same idea; the drawer's ranked actions are what can be acted on.

## Phase 12: levels of insight, project lines, and the real start context of a sub-agent (owner, 2026-11-24/25, found by using it)
The owner's reason for D28: "levels of insight: high, medium, low according to the number of tracks". The finding behind it: on one track the report says "Run the plan run in a sub-agent or a fresh session" (rule `where`), but it never reached the Agent recommendations drawer or statistics.md, because an action was listed only when it fired on at least 3 of the last 10 tracks and `where` fired on 2 (10155 and 10154): the warning on one track did not aggregate.
- D28 (owner) Levels. The drawer and the `## Recommendations` of statistics.md rank by LEVEL: how many of the measured tracks among the looked-at ones (the last 10) an action fired on. High = at least 60 percent of them, Medium = at least 30 percent and under 60, Low = at least one track and under 30 (constants `HIGH_SHARE` 60 and `MEDIUM_SHARE` 30 in `explain-rank.mjs`; whole-number arithmetic, so 3 of 5 is High). Every action that fired on one track or more is listed, High then Medium then Low; inside a level by count, then tokens, then the order of the rules (`RULE_IDS`); each carries its level word and its count line ("6 of 10 tracks ..."). The list is cut at five (`MAX_ACTIONS` 5, was 3 by D21). The whole list keeps the floor of 3 measured tracks (`MIN_TRACKS`: "Not enough tracks with statistics yet (N of 3)") and the quiet state ("No change suggested across the last N tracks.", now only when no action fired on any track). This replaces the per-action minimum of 3 tracks (D22). One function serves both: `rankRecommendations` and `rankFromExplains` give every action a `level`; the drawer reads it from board.json `rec.actions[].level` and shows a small badge; `rankedStatisticsLines` prints `- High: <title> (<count line>).`. The Copy buttons and the Discuss prompts are unchanged, except that Discuss all puts the level before each action.
- D29 (owner) Two project-level lines in the `## Insight` of statistics.md, with no threshold (they are counts): (1) `Lane runs by where they ran: N in a sub-agent, M in the main session (X percent in a sub-agent)`; (2) `Main-session lane runs that started with 400,000 tokens of context or more: A of M; median context at start: X in the main session, Y in a sub-agent`. The owner wrote 200,000; the existing constant `LONG_CONTEXT` is 400,000 (the limit of the `where` rule), so the line uses the constant and says its value. Numbers only. Where the data comes from: the short plan table is per phase on a single-run track, so it cannot give one entry per lane run; each explain.md therefore gets a second fenced block, `json lane-facts`, right after `recommend-facts` (which is unchanged): `{"v":1,"runs":[{"where":"sub-agent"|"main","context":N}]}`, one entry per lane run with replies of its own that is not a shared window; `context` is the Context at start shown in the short plan. A reader that does not know the block ignores it; an explain.md without it counts as not measured for these two lines, and the line says how many tracks were not counted (or says "not measured yet" when none has the numbers).
- D30 (owner) Context at start of a sub-agent run. Investigated first, read-only on the real transcripts (numbers only). Cause, two defects: (1) the short plan's Context at start was `firstContext`, the first reply of the main session in the lane window (D10), while the Where column is decided by reply share, so a row marked sub-agent printed the main session's context (10146 implement 788,792; 10143 implement 418,606) although a sub-agent starts near 55,000 (the first reply of 117 sub-agent transcripts: median 54,647); (2) the sub-agent starts of a run took each sub-agent's first reply inside the lane window, not its own first reply, and the reader dropped every line before the first lane window, so an agent that began earlier and kept working was counted at its mid-run context (10143: 196,849 and 230,403 against true starts of 12,781 and 12,902). Fix: the reader keeps the first reply of each sub-agent FILE before any window cut (`start` in `readTranscriptFile`, `startContext` on its messages); a run's `subStarts` are those own first-reply contexts; a row marked sub-agent shows their median (several sub-agents in one row: the median, the same figure as the Detail line; this is a choice the owner can change), a main-session row keeps the first reply of the main session; phase rows work the same way (`subStarts` per phase); the main session's `firstContext`, the `where` rule and the Insight context line are unchanged. After the fix, with `--now 2026-11-24T12:00:00Z`: 10146 implement 56,029 (was 788,792), 10143 implement 12,842 (was 418,606).

## Open questions
- Does a plain CLI session use the same folder layout for sub-agents and the same fields (the probe above was the desktop app)?
- How should a message be attributed when two tracks were worked in the same minutes (a parallel dispatch)? D3 says approximate; check how often it happens before building more.

## Probe results, Phase 1 (2026-11-21, implement lane)
- Same layout in a CLI session (`entrypoint: cli`) and in an sdk-cli sub-agent file as in the desktop app: `sessionId`, `timestamp`, `cwd`, `gitBranch`, `requestId`, `message.id` and a `usage` record on every assistant line; sub-agent files carry `agentId` and a `.meta.json` next to them whose description names the track (only the digits are used). Answers the first open question.
- One API response is written once per content block (thinking, text, tool_use), each with the same usage: in the probed session 13,773 assistant lines are 6,828 responses. Counting lines would roughly double every number, so the script counts per message id (a streaming line can hold a smaller output count, so the largest value wins). This corrects the "about 13,700 messages" figure in the probe findings above.
- Parallel dispatch (second open question): a sub-agent run is attributed by the track number in its meta description, a worktree session by branch `track-N` or folder `.worktrees/N`; only main-session messages written in the same minutes remain ambiguous and are counted in the window of every track whose lane run covers them (the approximation note says so).
- Many tracks have no claim commit (the lane goes queue to success, or plan success to review queue). The script then infers the lane that was next in line and marks the row "(no claim commit)"; its window includes queue waiting. Statistics keep claimed, inferred and still-running rows apart.

## Findings, Task 10 (2026-11-21, `lc-explain.mjs` on 10154, 10146, 10114, 10116)
Check (TC-7): per lane run, responses and all four token kinds equal an independent recomputation (dedupe by request id, separate code) exactly on 10154 (3 runs), 10146, 10114 and 10116; the one first mismatch (10114 plan, minus 10 percent) was other tracks' `.worktrees/N` messages that the independent script had not excluded. All numbers below are approximate (tracks overlap in time, the machine does other things, machines differ).
- Cache reads dominate: 10154 read 15.8M cache tokens against 43.6K output (about 360 times) in 79 responses; 10146 read 106.6M against 196.9K output (about 540 times) in 401 responses. Every response re-reads the whole session context: 200K on average (10154), 266K (10146); the first response of a lane run in the long-lived main session already holds 646K to 958K tokens of context. Cache created is only about 1 to 1.5 percent of the cache read.
- The lane-text hypothesis (27 KB, about 7K tokens per lane command) is small next to that: about 3 percent of one response's context and paid once per run. Sub-agent runs start much lighter (median 35K to 57K tokens of context against 95K to 770K for the orchestrating session), so work done by a sub-agent in its own worktree is cheaper per response than the same work in the long session. In 10128 sub-agents did 66 percent of responses and 44 percent of output.
- Biggest inefficiency: lane work run inside one months-long session (the context grows to near 1M tokens and is re-read on every reply). Second, process hygiene: lanes never closed ("quality-gate (still running)" on 10130, 10133 and 10141 to 10145, about 66 hours) and lanes never claimed (queue straight to success), which makes their time unmeasurable; about half of the tracks surveyed have only inferred windows. Human time shows only where `(HUMAN)` tasks or waiting statuses exist (10154: 3 of 20 minutes); a question put to the human (AskUserQuestion) is shown as a note, not counted.
- Repeated reads: 0 on every track checked; slowest tool steps are Bash calls of 40 to 60 seconds (tests, publishing), no pattern worth a fix.
- For the owner (Task 11, not done): have the lanes run the script at completion (base text, separate track), and consider whether lane work should default to sub-agents or fresh sessions.

## Probe 2, task 25 (2026-11-22, implement lane; read-only, numbers only)
Run on this machine's transcripts: this project (15,819 files, 124 of them sub-agent files, 51,852 distinct replies) and Otralingo (2,138 files, 1,440 sub-agent files, 57,835 distinct replies). Replies are counted once per message id, as the reader does.
- Model per reply: `message.model` is on every distinct reply (51,852 of 51,852 and 57,835 of 57,835). Main sessions and sub-agents both use several tiers (opus, sonnet, haiku ids). Two kinds of id are not a tier: `<synthetic>` (4,286 and 90 main-session replies: no model answered) and ids with no tier word, such as `claude-fable-5` (1,125 replies in this project). The reader must allow-list the id, and the tier of such an id is "unknown" (no model recommendation).
- Thinking tokens: `usage.output_tokens_details.thinking_tokens` is MISSING on most replies: present on 19,636 of 51,852 (this project) and 23,465 of 57,835 (Otralingo), above zero on 11,648 and 12,122. Where it is recorded, thinking is 5.5M of 11.9M output tokens (46 percent) and 4.0M of 16.9M (24 percent). So an absent field must read as "unknown", not zero, and the share is taken over the replies that record it.
- Effort: the top-level `effort` is a string on 92,294 of 97,039 assistant lines here ("high" 91,491, "medium" 803) and 108,634 of 109,091 on Otralingo (nearly all "medium"); `perTurnEffort` is on fewer lines (17,795 and 108,243) and is sometimes null (416). On the 125,185 lines that carry both as strings they never differ (0), so the reader takes `perTurnEffort` when it is a string, else `effort`; a reply with neither is "unknown" (4,720 assistant lines).
- Missing or not measurable: failed tool steps (the reader keeps no error flag), the command or file behind a step (by design, REQ-4), and any cost. Sub-agent files carry the same three fields as main sessions.
