**Problem**: Confirmed by reading the source (not from the reported symptom alone): when a specific project is selected, usePolling.js hits GET /api/projects/:id/tracks, which is genuinely server-scoped via a SQL WHERE project_id = ... clause -- that path is efficient and does not need fixing. But in "All Projects" view (selectedProjectId === null), usePolling.js:72 calls the unscoped GET /api/tracks instead, whose handler (ui/server/index.mjs:1365-1401) runs ONE query joining every track row in the ENTIRE database across every project -- no LIMIT, no project filter -- plus three correlated LATERAL subqueries per row (most recent comment body/author/created_at, an unreplied_count scan over track_comments, and a human_needs_reply computation), so the server-side cost is O(total tracks in the whole install) on every single poll tick, not just the payload size. The full result set (currently 737 tracks across 19 projects in this local DB) is then shipped whole to the browser and ONLY THEN split per project client-side: ProjectCard.jsx:34 does tracks.filter(t => t.project_id === project.id) inside each card render. This repeats on every poll cycle -- usePolling.js polls every 2000ms by default and every 30000ms once the websocket connects (POLL_INTERVAL_DEFAULT / POLL_INTERVAL_CONNECTED) -- so the entire database's track list, including three per-row correlated subquery results, is recomputed and retransmitted on a fixed short interval regardless of which project(s) the user is actually looking at. Every additional track created in ANY project on the install makes the All Projects overview slower for EVERY user viewing it, with no ceiling. Needed: stop shipping full per-track rows for a view that only needs per-project summary counts. At minimum, add a dedicated summary endpoint (e.g. GET /api/projects/summary) that computes per-project aggregates in SQL (COUNT(*), counts by lane_status, unreplied totals) via a single GROUP BY instead of one row per track, and have the Projects overview page (ProjectsPage/ProjectCard) consume that instead of the full unscoped list; the full per-track /api/tracks payload should only be requested for a project once its card is actually opened/expanded, not eagerly for every project on every poll while the overview is showing. Verify against a realistic-scale dataset (the existing 737/19 in this local DB is a reasonable floor), and confirm the fix does not regress the inbox badge count (tracks.reduce over unreplied_count, App.jsx) or the KPI rollup panel, both of which currently read off the same eagerly-fetched all-projects tracks array.
