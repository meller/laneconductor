**Problem**: Confirmed live on track 10065: its merge attempt correctly failed (unrelated git history, refused to force through), landing in `lane_action_status='failure'`. `KanbanBoard.jsx`'s `DONE_LANE_STATUS_CONFIG` (added by track 10035/REQ-9, deliberately replacing an earlier git-state-based split) only maps `queue`→"Unmerged" and `waiting`→"PR open"; `failure` fell through to the generic base "Failed" label, invisible under the "Unmerged" heading this lane exists to surface. Meanwhile the Worktrees panel — computed by `worktree-audit.mjs`, cached via `refreshWorktreeSummaryCache()` — correctly still showed it as needing a merge, because it classifies from real git/GitHub state (`mergeable`/`stranded`/`conflicted`/`pr-open`/`open`), independent of `lane_action_status` entirely. The two views disagreed the moment a merge failed instead of just not having been attempted yet — a stopgap was applied directly to `KanbanBoard.jsx` (adding a `failure` entry) to fix this one case, but the underlying architectural gap remains: two independent computations of the same fact, free to drift again for any other reason `lane_action_status` and git reality disagree.

**Design principle to build to, confirmed with the user**: git (and, for PR-mode tracks, GitHub's PR-merged state — not raw local ahead/behind, which can lag a merge) is the source of truth for "has this track's code actually shipped." The DB should reflect that, not the reverse. This isn't "always trust git over the DB for everything" — which *lane* a track occupies (plan/implement/review/quality-gate/done) is legitimate workflow state that only the app tracks. But *within* the done lane specifically, "is it actually merged" is a git/GitHub fact, and `worktree-audit.mjs`'s existing classification already computes it correctly for both merge modes (direct: real ahead/behind/conflict; pr: whether the PR is actually merged, per D18's own reasoning for why `pr-open` must never fall through to the plain-merge `mergeable` classification). This matches a repeated pattern this session already found and fixed elsewhere: app/DB bookkeeping drifting from git reality (track 10063's wrong-folder writes, the stale-`running` orphan-reconcile gaps, the doc-sync reversion bug) — every time, the fix was "trust git, make the display/DB converge to it," not the other way around.

**Scope for planning**: (1) wire the same classification `worktree-audit.mjs`/`refreshWorktreeSummaryCache()` already computes into whatever payload feeds the Kanban board per track, so `KanbanBoard.jsx`'s done-lane grouping reads it directly instead of inferring "unmerged" from `lane_action_status`; (2) decide what happens when they disagree — does the reconciler actively correct `lane_action_status` to match the classification (self-healing, matching this session's `trustRunningStatus`-style fixes), or does the UI just render from the classification while leaving `lane_action_status` as a separate (possibly stale) field for other purposes; (3) revert or fold in the `failure`-label stopgap already in `KanbanBoard.jsx` once the real fix lands, so there isn't a redundant/conflicting second mechanism; (4) audit whether any OTHER lane's grouping or the Inbox's bucket logic has a similar DB-only assumption about "merged" that could exhibit the same drift.
