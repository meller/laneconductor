**Problem**: LaneConductor has two independent implementations of one collector API: ui/server/index.mjs (local, port 8091) and cloud/functions/index.js (Firebase). A worker talks to whichever it is pointed at. Nothing at runtime ever checks that the server on the other end implements the contract the worker expects, and the drift is silent every time. No version negotiation exists anywhere. POST /worker/register sends hostname, pid, project_id, mode, cli, model, available_models and worktrees, and no API or protocol version. Neither server reports a version. Nothing compares them. Confirmed live 2026-09-03, the two servers already disagree on their most basic endpoint: GET /health returns {ok:true,cloud:true} from the cloud function (cloud/functions/index.js:328) and 404 Cannot GET /health from the local server, which has no health route at all. The endpoint you would naturally use to ask what am I talking to exists on exactly one of the two. Worse, the worker actively mis-diagnoses a missing route. In the heartbeat error path (conductor/laneconductor.sync.mjs:1253) a 404 is treated identically to a 401 and triggers upsertWorker() to re-register, on the assumption that the worker record vanished. A 404 actually means this server does not implement that route. Against a server missing the route the worker will re-register forever and never surface the real cause. There is already a confession of this failure mode in the code at laneconductor.sync.mjs:2765, from track 10053: a transition call was sending POST to a route registered as app.patch in both servers, so it 404'd every time, and the comment records that it went unnoticed because the .catch() only warns. That call was dead weight for an unknown length of time and was found by conductor/tests/cloud-route-parity.test.mjs's control assertion, not by anything at runtime. This is the root pattern behind both track 10052 (Firebase rewrite globs silently returning the SPA's HTML for 24 of 27 endpoints) and track 10053 (11 route families missing from the cloud function outright). In both cases a worker registered successfully and then failed at everything real, and a human had to notice the weirdness and go digging. The parity test now catches drift at build time in this repo, but nothing catches it at runtime, and nothing at all catches a deployed server simply being older than the worker talking to it, which is the normal state of affairs the moment there is more than one machine. Desired behaviour, decided with the product owner: warn and continue degraded, do not hard-fail. A version mismatch must be loud and visible in the UI and worker log, but must not strand a worker that is pointed at a slightly stale deploy, since hard-failing would turn every routine deploy lag into an outage. Scope to work through in planning: expose an API version and a capability or route manifest from both server implementations, keeping the two in one shared source of truth rather than two hand-kept lists, since a hand-kept list is exactly what let track 10052's WORKER_PATHS silently omit /conductor-files; have the worker fetch and compare it at registration and record the result; surface a mismatch in the UI where a human will actually see it, not only in the log; and stop conflating 404 with worker-not-found in the heartbeat error path so a missing route reports itself as a missing route. Add a health route to the local server so both ends answer the same basic question. Consider whether the manifest check should also run periodically rather than only at registration, since a server can be redeployed under a long-lived worker.
