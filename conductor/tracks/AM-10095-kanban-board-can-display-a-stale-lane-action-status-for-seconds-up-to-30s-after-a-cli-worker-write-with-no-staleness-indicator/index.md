**Problem**: Confirmed by reading the source end-to-end, not from the reported symptom alone: bin/lc.mjs's shared move-family handler (plan/implement/review/quality-gate/backlog/done/pulse/rerun/move, ~line 2962) writes a lane transition DIRECTLY to the track's index.md via a plain writeFileSync (line 3062) -- it makes no HTTP call to push that change anywhere. The only network call in that handler is the unrelated session-invalidation DELETE /track/:num/session. The same is true of the worker's own in-file running-claim write in autoLaunchLocalFs (conductor/laneconductor.sync.mjs). Because the browser board (ui/src/App.jsx via usePolling.js) reads exclusively from the Postgres-backed API, not the filesystem, the DB -- and therefore the board -- only learns about a CLI-or-worker-driven lane/status change once the SEPARATE, already-running sync worker process notices the file changed via its chokidar watcher, waits out a 250ms debounce (debounce(f, ..., ms=250) at conductor/laneconductor.sync.mjs:2024), POSTs the whole file to the local collector (POST /track, ui/server/index.mjs), which writes the row and only then calls broadcast(\"track:updated\", ...) (ui/server/wsBroadcast.mjs consumer). The browser's own onWSMessage handler (ui/src/hooks/usePolling.js:118-134) further debounces that event by another 500ms before it actually re-fetches. So there is a real, structural propagation window -- typically under ~1-2 seconds end to end, but with no upper bound guaranteed -- during which the file (and any already-spawned CLI child process) says one thing (e.g. Lane Status: running) while the rendered Kanban card still shows the PRIOR status (e.g. queue) with no visual indication that the board might be stale. If the websocket broadcast is ever missed, dropped, or coalesced with another event for the same track, the ONLY fallback is the next scheduled poll -- every 2000ms normally, but up to every 30000ms once the websocket is reported connected (POLL_INTERVAL_CONNECTED, usePolling.js) -- meaning the mismatch window can silently widen to as much as 30 seconds with no user-visible signal that a refresh is overdue. Reproduced by direct observation this session: ran `lc plan 10094` / `lc implement 10093` from the CLI, immediately confirmed via direct file read and a direct DB query that Lane Status already read `running` and a real child process was already spawned, while the Kanban board (loaded moments earlier) still displayed the pre-transition status until its next poll/broadcast cycle caught up. Needed: (1) decide whether a CLI-driven lane transition should push its own change immediately (e.g. bin/lc.mjs calling the same local collector endpoint the worker uses, POST /track or PATCH /track/:num/action, synchronously after the file write, in local-api/remote-api mode) rather than relying entirely on a second process's file-watch cycle to notice; (2) add a bounded, user-visible staleness signal to the board (e.g. a relative \"synced Xs ago\" indicator already partially supported by usePolling's existing lastUpdated state, or a lightweight per-card pending/optimistic state) so a genuinely stale render is distinguishable from a confirmed-fresh one, rather than looking identical; (3) verify the fix does not reintroduce the double-fetch/abort storm that Track 10013's coalescing fix (usePolling.js inFlightRef/pendingRerunRef) was written to prevent.
