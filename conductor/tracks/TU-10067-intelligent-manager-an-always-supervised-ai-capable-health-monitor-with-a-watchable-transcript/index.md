**Problem**: Tonight's entire session was, in effect, a human plus one AI agent manually doing the job of a supervisor that does not exist: noticing a worker had silently died and stayed dead for 1h45m, clearing stale locks left by dead PIDs (both the global main-mode lock and per-track git locks), recovering orphaned dispatches with no run marker, catching the board lying about state (queue while genuinely running, done:success while not actually merged), catching Auto Run writes landing in the wrong duplicate folder and flapping back, killing leaked duplicate worker processes burning CPU for hours, and correctly diagnosing a Claude capacity probe that was actually an auth/billing failure. None of this was caught automatically. Ask, discussed live with the user: build this as an actual capability of the existing --manager worker type (conductor/laneconductor.sync.mjs, gated by the isManager flag, currently used only for machine-level provisioning per track 1089/1091) rather than inventing a new service. A manager is already running for this project today (worker id 1110, PID 16266) but has no periodic health-sweep loop of its own at all right now - grepping isManager in laneconductor.sync.mjs turns up only 15 references, essentially all about registration/identity, none about ongoing monitoring. Three explicit requirements from the user, verbatim in spirit: (1) something that makes sure the manager itself stays alive - the exact systemd-supervision pattern already built and verified tonight for the regular worker (conductor/systemd/laneconductor-worker@.service, Restart=always, verified live via a real SIGKILL-and-recover test) should be extended to cover a --manager instance the same way, since right now nothing supervises the manager any more than it originally supervised the regular worker; (2) a periodic intelligent sweep, looking at everything every X seconds; (3) visibility and interactivity - the user must be able to see what it is doing and talk to it through transcripts, explicitly comparing this to how a regular dispatched lane action already works (Show live session transcript, the Conversation tab, WorkerChatPanel) - this is not asking for a new UI paradigm, it is asking for the manager's own supervisory work to be a first-class, watchable, chattable session the same way every other dispatch already is. Proposed two-layer design, discussed and reasoned through live with the user before this track was filed, worth carrying into planning as the starting point rather than re-deriving: Layer 1, a fast deterministic sweep with no LLM involvement, cheap enough to run constantly on a short interval, checking specifically the failure classes this exact session hit - stale global main-mode lock with a dead PID, stale per-track git locks with a dead PID, worker heartbeat gone silent past a threshold, a claimed dispatch with no run marker past a conservative grace period (see track 10065's own no-marker fallback, which is the same category of check, just scoped to individual reconciliation rather than a standing sweep), duplicate worker processes for the same identity, and a board/DB state that disagrees with the worktree's own index.md (see track 10063, which is literally the bug class that made tonight's board display untrustworthy). Layer 2, an AI escalation path for the cases that are not safe to resolve by fixed rule - is this merge genuinely stuck or just slow, is this board mismatch a real bug or a normal in-flight race, is a dirty-checkout block real unrelated work or safe routine churn - dispatching a scoped session (same spawn mechanism every lane action already uses) to actually look and decide, with its reasoning and actions landing in a transcript and conversation.md exactly like any other dispatch, so req (3) above is satisfied by construction rather than bolted on. Open decision, explicitly NOT resolved yet and flagged for planning rather than defaulted: how autonomous the layer 2 escalation path is allowed to be. Options discussed but not chosen between: diagnose and report only; auto-fix things that are safe by construction (dead-PID lock cleanup, restarting a crashed process, correcting a board display value) but always ask before anything touching production or a merge; or full autonomous operation matching everything a human plus this AI agent did by hand tonight, including unattended done-lane merges and production writes. This decision materially changes the design and must be made explicitly during planning, not assumed. Also worth deciding during planning: interval length and whether it should be configurable per project; whether layer 1's checks belong in the manager process itself or could run from any worker (a manager may not be running for every project, but a regular worker already is); and how layer 2's AI sessions should be rate-limited or budgeted so a bad sweep interval does not turn into runaway API spend.
