# Track AM-10103: lc worker stop/restart has no systemd awareness — worker silently comes back after Restart=always

**Lane**: plan
**Lane Status**: queue
**Progress**: 0%
**Phase**: New
**Type**: dev
**Merge Mode**: direct
**Auto Run**: no
**Author**: AM
**Created By**: 2565050+meller@users.noreply.github.com
**Problem**: On machines where the LaneConductor heartbeat worker runs under a systemd --user service (confirmed live: laneconductor-worker@home-meller-Code-laneconductor.service, Restart=always, RestartSec=20s, alongside sibling laneconductor-api.service and laneconductor-ui.service units), 'lc worker stop' (bin/lc.mjs, top-level command==='stop') only ever kills the tracked PID via stopAndConfirmDeath and removes the pidfile. It has zero awareness of systemd. Killing the process just triggers Restart=always, which silently relaunches the worker about 20s later, re-acquiring its identity lock (conductor/.sync.lock-target) and its DB workers-table registration. Confirmed live during AM-10099's implement dispatch: 'lc worker stop' printed 'Worker stopped', but the very next 'lc worker run 10099' failed with 'Another live worker already holds this identity's lock', and a retry shortly after failed again with 'Refusing to start -- 1 live base worker identity already registered' (AM-10093's own cap, now tripped by a worker systemd itself brought back). The only way to actually stop it was 'systemctl --user stop laneconductor-worker@home-meller-Code-laneconductor.service' directly, bypassing lc entirely. This is the same class of bug the AM-10093/AM-10099 line of tracks exists to catch -- state silently reverting behind an operator's back -- just at the process-supervision layer instead of DB/file sync, and it directly undermines the documented 'stop the existing worker first (lc worker stop)' guidance that AM-10099's own --force-run fix and other error messages rely on. Note there is already systemd-awareness precedent in this codebase: hasSystemdUser()/systemd-user.mjs (writeUnit/startService/stopService/isServiceActive/getServicePid) is already used by the 'lc api start' path (Track 1079), but 'lc worker start/stop/restart' (the heartbeat worker itself) never adopted it, despite systemd units for the worker existing and being enabled on real machines. Planning should confirm the fix shape, but the natural one is: lc worker stop/start/restart detect whether a systemd unit exists/is active for this project's worker (mirroring hasSystemdUser()) and go through systemctl --user stop/start in that case, falling back to the existing PID-file path on non-systemd machines.
