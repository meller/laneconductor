**Problem**: Execution order 3 of 5. North star: one codebase, three deployment profiles -- standalone (worker + hub-capable), hub (org management, worker-less), federated hubs (private-tracker worker sharing). Sovereign, vendor-agnostic, customer-owned. Vendor-hosted multi-tenant (TU-10048) is v3/later. This track is the v1.5 revenue unlock: a single-tenant standalone instance a customer deploys into their own Azure subscription -- a dev-machine-class VM (16GB RAM minimum) with Postgres, the API/UI, a worker and the agent CLI pre-installed and auto-starting -- as an Azure Managed Application (MSP/publisher-managed model: the publisher gets delegated access into the customer resource group for support and updates). Hub-capable by design from day one: the setting "which hub am I registered to" (the existing collectors array) ships present-but-off, so the same image later joins a hub (AM-10101) with a config change, not a rebuild. First run is driven by the manager worker, not a 23-question readline wizard: most of lc setup infra questions (DB host/port/password, mode, collectors) are fixed at image build time; the only non-AI step is a bootstrap secrets form (Claude API key -- the ToS-clean org-key path and the only thing that works headless -- plus admin credential/TLS), after which the manager, seeded with set-up-this-machine instead of create-a-project (the existing Create with chat flow, 1091 Phase 7 / AM-1119), collects repos, git access and optional hub registration conversationally. Secrets never go through the chat: the manager asks, but values land via secret-field forms into .env/the secret store, never into conversation.md/the DB (Zero-Secrets Policy). Blockers already found by the unrequested auto-plan pass and confirmed against source: REQ-1 ui/server/index.mjs:176-213 installs a global middleware that forwards any request whose hostname is not localhost/127.0.0.1 to a hardcoded Cloud Run URL -- a customer reaching their own VM by DNS/IP would have every API call served by the vendor cloud (functional break and a sovereignty violation); must be off unless explicitly enabled. REQ-2 server.listen binds all interfaces while loadAuthConfig sets AUTH_ENABLED=false without a Firebase project, which is the standalone case -- an unauthenticated API that spawns agent CLIs and runs git is remote code execution on a routable interface; needs loopback-by-default plus a local auth mode with no Firebase dependency. REQ-7 no work happens without an installed and authenticated agent CLI -- the listing must state the prerequisite, first run must verify auth (not just --version), and the UI must show an unmistakable no-provider state. Also from that pass: serve a built UI (vite build) not the dev server; path-portable systemd units (all three hardcode /home/meller); no default postgres/postgres credentials and no published DB port; pinned image tags + lc update with Atlas baked in and migrations on boot; fixed project path convention; no license gate (ELv2 already forbids licensees from re-hosting; confirmed by reading LICENSE -- it does not restrict the copyright holder distributing via a marketplace); no telemetry by default (lc support-bundle instead). One recorded disagreement to settle in re-planning: the auto-plan (spec.md D-1) recommends a plain marketplace VM image over an Azure Managed Application on sovereignty grounds (publisher-managed resource group); the product owner prefers the Managed Application/MSP model for support and updates. Related: 1120 (real-credential deploy verification), AM-10099 (release-readiness gate, hard dependency), AM-10100 (run ledger, ships single-node), AM-10101 (hub), TU-10048 (v3/later vendor-hosted).
**Summary**: v1.5 revenue unlock -- single-tenant standalone Azure Managed Application image (16GB dev-class VM, Postgres+API/UI+worker+agent CLI pre-installed), hub-capable by design, manager-driven first run behind a one-form secrets bootstrap; three blockers already identified (hardcoded cloud proxy, unauthenticated all-interface bind, customer-supplied authenticated CLI).
