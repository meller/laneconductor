**Problem**: Confirmed live and reproduced repeatedly on track AM-10089 today: lc plan 10089 correctly writes Lane: plan to index.md and correctly triggers a file-to-DB sync event every single time (visually confirmed in the UI Conversation tab - the same "Moved to plan (via file sync)" comment fired 5+ times over several minutes) - yet the track kept ending up back at Lane: done within seconds each time, both in the file and in the DB. Caught the live mechanism once directly: immediately after writing plan, the actual dispatched process was a RESUMED session running /laneconductor merge 10089 (not plan) - meaning the auto-launch loops own decision of which lane action to run next was based on a STALE view of the tracks state that still said done:queue, not the just-written plan:queue. That stale merge action then completed normally (a no-op, since the code was already merged) and wrote Lane: done right back, erasing the correct change with no error anywhere. Separately, and likely a major contributing/compounding factor: this session accumulated 9+ distinct worker identities (differing --worker-number values, e.g. 1, 20007, 20008, 20012, 20014, 20015, 20018, 105, 106) all simultaneously alive and registered against the same single primary laneconductor project, from many restarts across a long session without ever stopping the previous instance. Confirmed via ps aux and the workers table. The existing per-identity worker lock (conductor/laneconductor.sync.mjs, acquireWorkerLock, .sync-N.lock-target) only prevents two processes from sharing the SAME worker_number identity - it does nothing to limit how many DIFFERENT identities can be registered and simultaneously polling/dispatching for one project. Each identity independently runs its own 5-second pullTracksMetadataFromDB (DB to filesystem pull, laneconductor.sync.mjs, setInterval at line 3780) and its own auto-launch claim loop, so with N concurrently-alive identities there are N independent chances per cycle for a stale pull or a stale dispatch decision to interleave badly with a fresh, correct write from any other source (a human lc plan/move invocation, or a different identity legitimate own completion). Stopping the excess duplicate identities down to just one during live debugging today measurably reduced but did NOT fully eliminate the revert - it kept happening even briefly after cleanup, so there is likely also a single-worker-scoped staleness bug in how the auto-launch loops own in-memory view of a tracks current lane gets refreshed relative to a just-written file change, independent of the multi-identity problem. Needed: (1) root-cause and fix the single-worker staleness path so a fresh, correct lc plan/move write can never be immediately overridden by a dispatch decision or DB pull that has not yet observed it - likely requires re-reading the tracks own current index.md state immediately before dispatching an action, rather than trusting a periodically-refreshed in-memory cache; (2) decide on and implement a real mitigation for the worker-identity accumulation problem itself - either actively preventing/limiting how many distinct identities can be alive for one project at once, or a periodic sweep that proactively retires idle duplicate identities beyond some small expected count, since this is very likely to recur in any long-lived deployment (exactly the kind of thing that would surface in a customer managed-app deployment if their own instance is restarted repeatedly during upgrades or crashes without clean shutdown). This is directly relevant to marketplace/managed-app hardening - a customer deployment that silently reverts real state changes for reasons invisible in the UI (no error, just a card that seems to "snap back") would be a serious trust and support-burden problem.
