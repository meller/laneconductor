**Problem**: Execution order 5 of 5 -- only after two real hubs exist somewhere. North star: one codebase, three deployment profiles -- standalone (worker + hub-capable), hub (org management, worker-less), federated hubs (private-tracker worker sharing). Sovereign, vendor-agnostic, customer-owned. Vendor-hosted multi-tenant (TU-10048) is v3/later. -- BitTorrent for discovery and reciprocity, work-queue with single-owner state for execution. Hubs are trackers: they exchange peer/worker lists; they do not execute. Swarm keyed by repo: a worker with the repo cloned and credentials is a seeder for that project, so capacity for project X is the set of seeders of X -- repo locality made explicit, and the genuinely hard part (a hub B worker on a hub A project needs A repo access and credentials). Reciprocity/ratio ledger on the run ledger: the shared resource is model quota on someone else machine; a ratio (contributed worker-hours vs consumed) answers whose subscription burns across teams. Trust boundary is a private tracker within an org (invite-only, ratio-enforced, hub-to-hub trust on top of per-worker machine tokens) -- a public swarm of strangers executing your code with your credentials is a research problem, not a product. Where the analogy must break: agent work is mutable, side-effecting, exactly-once and ordered, verified by review/quality-gate not by a hash -- so the owner hub stays authoritative for track state, peers lend execution only, results flow back through the owner (composes with ownership-per-project without reintroducing multi-master). Closest prior art: HTCondor flocking (cross-pool job sharing), Petals (BitTorrent-style inference sharing -- stateless, unlike this). Open: hub-to-hub auth and revocation, cross-hub attribution in the run ledger, failure of a peer mid-run (lease + reclaim), and per-org policy for which projects may ever leave their home hub.
