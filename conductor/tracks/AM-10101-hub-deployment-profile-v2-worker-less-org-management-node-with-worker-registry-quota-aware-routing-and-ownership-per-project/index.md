**Problem**: Execution order 4 of 5 (after the standalone image, AM-10098). North star: one codebase, three deployment profiles -- standalone (worker + hub-capable), hub (org management, worker-less), federated hubs (private-tracker worker sharing). Sovereign, vendor-agnostic, customer-owned. Vendor-hosted multi-tenant (TU-10048) is v3/later. -- Key fact: the hub is the same server as the standalone (ui/server Express + Postgres) run as a deployment profile -- no worker doing lane actions (the existing --manager / sync-only mode), exposed on a network with auth on -- not a second codebase. Standalone instances register their worker with a hub by pointing their collectors array at it (remote-api mode already does this; a hub-in-a-VM sidesteps the fragile hosted-collector path of track 10052 entirely). Scope: (1) Profile and exposure: worker-less image/compose profile; TLS; a local auth mode that does not require Firebase; loopback-by-default elsewhere (shares REQ-2 with the standalone track). (2) Worker registry view: every registered worker across machines with hostname, owner, visibility (private = visible for accounting, not claimable; team/public = pooled -- workers.visibility already exists), available_models, collector_health, and per-worker quota state (provider_status generalized from per-project to per-worker: available / exhausted / reset_at, plus observed consumption from the run ledger). (3) Quota-aware routing: placement = has-repo AND has-model AND has-quota; an exhausted worker stops claiming so queued work flows to headroom (the pull-based claim-queue makes this nearly free); sticky within a lane action (moving mid-run loses the --resume session), free to move between lane actions; capability matching at claim time as workflow.md already anticipates. (4) Ownership-per-project: each project has exactly one authoritative home hub (the existing collector-0-authoritative rule, applied per project); nodes can own some projects and be clients of others; manual re-homing first, leases later. No multi-master writes on any project -- the invariant that keeps the AM-10093 race class tractable. (5) Org views on the run ledger: cost per track/project, per-seat consumption vs per-employee demand, chronically-capped vs chronically-idle seats, resize recommendations for the admin. Credential-neutral by design (org API keys, Teams/Enterprise plans, personal seats); before any cross-seat pooling is marketed, verify the Anthropic Teams/Enterprise terms on one seat usage being consumed by another user workload with org consent -- if not allowed, routing matches work to each user own seat headroom and everything else still ships. Prior art to borrow, not reinvent: CI runner pools (GitHub/GitLab/Buildkite) for pull-based claiming with capability labels.
