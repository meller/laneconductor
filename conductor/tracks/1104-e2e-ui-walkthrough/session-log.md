# Session Log: Track 1104 — E2E UI Walkthrough

Real browser session (headless Chromium via the `playwright` npm package,
scripted step by step — screenshots captured at every step) against a
running local instance (`localhost:8090` / `:8091`). Run across two
sessions: the first was killed mid-way (exit 143) after step 4/Activity;
this log reconstructs its screenshots/state and completes the remainder.
Scripts live in `conductor/tests/scratch-1104/`.

Every entry below is what was **observed**, not what was intended.

## Step 0 — No manager worker available

`+ Project` on a project selector with no manager worker registered shows
a blocking modal: *"No manager worker is available. A manager is a
machine-level singleton — start one on whichever of your machines should
host new projects,"* with the exact fix command
(`lc worker start --manager --projects-dir <path>`) and the known machine
name. Accurate and actionable — no finding here.

## Step 1 — New Project wizard

After starting a manager worker, `+ Project` shows the real form: project
name, repo source (existing path / git URL toggle), an "already has code"
checkbox, description, tech stack, KPIs. Filled in as a brand-new project
(unchecked "already has code") pointing at a clean throwaway directory.
Clicking "Create Project" showed live status text inside the modal
(`pending` → `claimed` → `done`), ending with the created path. **Matches
1102's "What worked."**

## Step 2 — Project registration + track creation

Selecting the new project in the project selector: appears immediately,
`repo_path` set, board empty ("No tracks yet"). The WORKERS bar shows
**both** a `MANAGER` worker and a project-scoped `SYNC-ONLY` worker,
labeled with the project name and model — hostname, mode, and project
scope all visible at a glance. **This is reference-outcome point #4
working correctly** — filed as a "what worked" note in 1102 rather than a
finding.

`+ Track` modal: Feature/Bug toggle, Domain (Dev/Mktg/Sales/Support/Other),
title, description. Created "Add a health check endpoint" → track `#001`
appeared in `PLAN` / `Queued for automation`, 0%.

Verified on disk (not just the UI): all 5 files
(`index.md`, `spec.md`, `plan.md`, `test.md`, `conversation.md`) exist in
`conductor/tracks/001-add-a-health-check-endpoint/`, and `test.md` is
real, non-stub content generated by the plan run (see Step 3) — not the
generic `(Test cases to be added)` placeholder.

## Step 3 — Triggering the Plan lane action (the main finding)

Opened the track detail drawer (Overview / Plan / Spec / Tests /
Conversation / Logs tabs, a "Run on worker" dropdown, and a "Run plan now"
button — none of this is gated behind a prior success state, unlike what
1102's F5 originally reported). Clicked **Run plan now**.

Observed over the following screenshots:
- Immediately after the click: no visible change for a few seconds
  (screenshots 11/12) — mildly concerning in isolation but explained by
  the next observation.
- Shortly after: the card correctly moved into a `RUNNING` section with a
  `WORKER ACTIVE: PROCESSING…` badge and a live `stale Ns` counter
  (yellow, climbing) — this part of the flow works.
- The **Live Transcript** panel (drawer's "Transcript" button, distinct
  from the "Logs" tab) showed the dispatched agent's real tool calls
  (Skill, Bash, Read, Write, Edit) live, ending in a clear final message:
  *"Track 001's plan is complete… `index.md` is transitioned to
  `**Lane**: plan`, `**Lane Status**: success`… The sync worker will pick
  this up on its next heartbeat and reflect it on the Kanban dashboard."*
- That never happened. The `stale Ns` counter kept climbing (yellow → red)
  indefinitely. Confirmed independently on disk and via the API, well
  after the run: the **worktree's** copy of `index.md`
  (`.worktrees/001/conductor/tracks/001-.../index.md`) has
  `**Lane Status**: success` and fully-written real content, but the
  **main** tracked copy (what the UI/DB actually reflect) still has the
  original stub with `**Lane Status**: running`. `GET
  /api/projects/925/tracks` shows `lane_action_status: "running"`,
  `lane_action_result: "stuck_timeout"` — self-contradictory, and the
  project's worker (`GET /api/projects/925/workers`) reports
  `status: "idle"`. The dispatch queue is empty (nothing left to retry).

**Filed as new finding 1102 F9** (cross-linked from here) rather than
duplicated in full — see that file for the complete writeup and fix
direction. In short: this is a *different* trigger than 1102's F8 (which
was an exception during worktree setup) — here the actual plan work
**succeeded** and is sitting complete in the worktree, but the "copy
artifacts back to main repo" step never ran, and the UI has no way to
show this or let a human recover it. `#001` is stuck at `plan/running`
forever from the UI's perspective.

Because of this, track 001 in the throwaway project never reached
`plan/success` from the UI. Per the track's own AC, this is filed as a
finding (F9) rather than worked around by re-triggering another way.

## Step 4 — Track detail drawer tabs

- **Plan tab**: unchanged stub content (matches the stale main-repo file,
  not the worktree's real output — consistent with the F9 finding above).
- **Conversation tab**: "No messages yet." — plausible; the plan run
  didn't hit a path that posts a conversation comment.
- **Logs tab**: raw, unformatted JSONL of the full `last_run.log` stream —
  technically "readable" (satisfies the letter of the AC) but not
  human-friendly. Minor UX gap relative to the Transcript panel.
- **Transcript ("Live Transcript") panel**: by far the best affordance —
  a clean, step-by-step rendering of the actual agent run, ending in its
  own plain-English summary. Noted in 1102 as a "what worked" / reuse
  candidate.

## Step 5 — Inbox

Clicking Inbox opens a panel: *"Active conversations across tracks" → "No
active conversations."* Accurate for this session (no human↔AI
conversation threads were active) — no finding.

## Step 6 — CI/CD tab + deploy wizard (stopped before deploying)

CI/CD tab has three sub-tabs: **Setup** ("Build your deploy.sh"),
**Config** ("Manage environments"), **Release** ("Dispatch & history").
Release tab, with no environments configured, shows a clear inline
warning (*"No environments configured. Go to Setup… or Config…"*) and a
disabled "Deploy to Env" button — good failure-state messaging, no
finding.

Clicked "Build New" → deploy wizard opens: a 5-step flow (Provider →
Database → Secrets → Environments → Preview). Reached step 1 (Provider),
which lists Google Cloud, AWS, Vercel, Fly.io, Custom/Other, with
Reset/Next controls. **Stopped here** — no provider was selected and no
further step was entered, per the track's requirement to walk but never
trigger an actual deploy.

## Step 7 — Deliberate failure observation

Step 3 above **is** the deliberate failure/limbo observation required by
the track's AC — no separate contrived failure was needed since a genuine
one surfaced organically. It reproduces 1102 F8's exact *symptom*
(board shows "running", Activity shows the worker idle) from a materially
different *cause* (a successful run whose completion never merged back,
vs. an exception during setup), which is why it's filed as a distinct
finding (F9) rather than merged into F8.

## Dogfooding note (meta)

This session log, and the findings above, were produced while working
Track 1104 itself. Actually triggering *this* track's own plan/implement
lane actions through the LaneConductor UI (rather than the worker/skill
dispatch mechanism that launched this Claude session) was not attempted
in this pass — the session was launched the normal way tracks are
launched (worker dispatch from the queue), which is itself one of the
project's supported paths, not a side channel. Driving Track 1104's own
lane transitions by clicking buttons in the browser (as opposed to the
target throwaway project used for the walkthrough) is left as an
explicit gap — see Phase 3.
