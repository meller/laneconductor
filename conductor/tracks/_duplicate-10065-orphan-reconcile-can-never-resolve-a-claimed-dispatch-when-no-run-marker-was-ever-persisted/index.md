# Track TU-10065: Orphan-reconcile can never resolve a claimed dispatch when no run marker was ever persisted

**Problem**: classifyOrphanedDispatch (conductor/services/orphaned-dispatch.mjs) only treats a worktree's Lane Status of running as safely reconcilable when runnerExited is PROVEN true, which requires a run marker (conductor/.runs/<track>.json) to have existed and then been shown dead via isRunMarkerLive. When no run marker exists at all, runnerExited stays undefined by design (REQ-6), and the first branch of classifyOrphanedDispatch requires runnerExited === true, so it falls through and the function returns orphaned: false, meaning still genuinely running, skip it. That is correct for the case it was built for, a marker that existed and is now provably dead, but it has no path at all for a claimed dispatch whose run marker was simply never there, so the dispatch is stuck permanently rather than in the normal 30 second grace window. Confirmed live 2026-09-04, track 10063, dispatch id 3428. A worker was restarted (systemctl restart, for an unrelated systemd migration) while the worker's own implement session for 10063 was in flight. The worktree's index.md correctly still read Lane Status: running afterward, but conductor/.runs/10063.json did not exist, ps confirmed the CLI process itself was dead, and the per-track git lock at .conductor/locks/10063.lock was still stamped with the old, now-dead worker daemon PID. The worker_dispatch row (worker_id 1112) sat at status claimed with no path to resolution, because the SAME worker identity id (1112) re-registered after the restart with a new pid and a fresh, zero-age heartbeat, so this is not even the already-fixed track 10054 case of a dispatch orphaned by a worker-identity change, the offline-workers reconciliation path never applies here since the identity looks perfectly alive. Resolved this one instance by hand: marked the dispatch failed with an explanatory result, released the stale lock file, and reset the track back to implement:queue in the worktree, the primary checkout, and the DB. Scope for a real fix: give classifyOrphanedDispatch or its caller a way to treat a claimed dispatch with a genuinely stale worker_dispatch.claimed_at (past the normal grace window used elsewhere) and no run marker at all as itself a signal worth investigating, rather than treating no marker the same as a marker that has not yet proven anything. Options worth weighing during planning: write the run marker earlier, before the child process is actually spawned, so a marker always exists for the whole lifetime of a claim rather than only once spawning has visibly started, closing the exact window this bug lives in, or add a distinct claimed-too-long-with-no-marker branch to classifyOrphanedDispatch that is more conservative than the existing runnerExited path, since the absence of a marker is weaker evidence than a marker proven dead, or, most directly, have the worker write and delete its own run marker as part of a graceful shutdown, so a deliberate restart like this one never produces this state at all, only a genuine crash would. This last option would not fully close the gap by itself, since a SIGKILL or host crash bypasses graceful shutdown entirely and the marker-absent scenario would still be reachable, so it is a mitigation for the common case rather than a complete fix. Also worth checking whether the per-track git lock should be released as part of the same graceful shutdown path, since it was also left stale here, stamped with the dead PID, and nothing currently cleans it up either.
