**Problem**: A single registered worker row can end up running multiple tracks' lane actions concurrently (parallel_limit > 1 for a lane), but the workers table only has one current_task/status/pid per (hostname, project_id, worker_number) — updateWorkerHeartbeat() upserts by exactly that key, so a second concurrent claim just overwrites the first claim's displayed task, not adds to it. Confirmed live: livingwork's single worker (worker_number 1) had two genuinely separate, independently-alive claude CLI child processes running implement on AM-1018 and AM-1019 simultaneously (parallel_limit: 2 for the implement lane) — both real, both progressing correctly — but the Workers panel could only ever display one of them as current_task, silently hiding the other's existence from anyone looking at that view. A UI-only patch (distinguishing genuinely-failing collectors from never-registered ones) shipped this same session but does not address this — it is a separate, narrower issue. Proposed direction (from a live design discussion, not yet validated in code): keep worker:pid:track strictly 1:1:1 — a registered worker identity should correspond to exactly one live pid running exactly one track's lane action, always. When the auto-launch loop wants to claim a second track concurrently (within the same lane's parallel_limit), it should register an ADDITIONAL worker identity (a new worker_number, or an on-demand worker row scoped to that one claim's lifetime) with that claim's own actual child pid, rather than layering a second concurrent claim onto the same worker_number's single-valued row. When that claim's process exits, its worker row should retire (or return to idle) independently of any other concurrently-running claim's own worker row. This makes the Workers panel accurately show N rows for N concurrently-running tracks, each single-valued and correct, with no data-model mismatch to patch around in the UI. Explicitly OUT of scope / a different mechanism entirely: genuine subagents (Task-tool orchestration within a single CLI turn's own internal tool use, e.g. how the manager's own conversational turns fan out to parallel Task calls for planning multiple tracks at once) are not 'workers' in this sense at all and should not get their own worker rows — those are an implementation detail of one CLI session's own turn, not a second unit of LaneConductor-level concurrency, and this track should not touch that path. Open questions for planning: how worker_number allocation should work for these on-demand, claim-scoped identities (a growing pool vs. reusing freed slots), what happens to a claim-scoped worker's row on a crash (same orphan-detection concerns as any other worker), and whether this should be scoped narrowly to auto-launch's own concurrent-claim path or generalized to every place a worker can end up running more than one thing (manual dispatch of a second action while one is already live, if that is even currently possible).
