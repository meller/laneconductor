# Track TU-10062: Claude capacity probe misclassifies an expired CLI login as rate-limit exhaustion

**Lane**: plan
**Lane Status**: running
**Progress**: 0%
**Phase**: New
**Type**: dev
**Author**: TU
**Created By**: test@example.com
**Problem**: checkClaudeCapacity() (conductor/laneconductor.sync.mjs:3641) spawns 'claude -p test' before every dispatch to check whether the primary provider has capacity. It treats any non-zero exit code as capacity exhaustion, unconditionally, and only tries to parse a real reset time out of stdout/stderr when the text contains 'hit your limit', 'exhausted', or 'resets' (line 3667). Any other failure reason - including an expired OAuth session - falls through to the same exhausted state with a hardcoded 'give it 1 minute and try again' default (line 3664, resetAt = Date.now() + 60000). Confirmed live 2026-09-04: the standalone claude CLI's login had expired ('Failed to authenticate: OAuth session expired and could not be refreshed', exit 1), completely unrelated to usage or rate limits - this is the plain CLI binary's own OAuth store, separate from a Claude Code app session's SDK-hosted auth (which is unaffected; this exact investigation was run from inside a live Claude Code session while the worker's own claude CLI calls were failing). Every dispatch in the project failed with lane_action_result 'no provider available' (buildCliArgs returning null at laneconductor.sync.mjs:6127/6138 when isProviderAvailable/checkClaudeCapacity both report unavailable and no secondary CLI is configured). Because auth failures do not self-heal by waiting, and the code always guesses a fresh 1-minute cooldown on every retry rather than remembering the failure was unparseable, provider_status.reset_at kept rolling forward every single retry cycle (09:34:04 dispatch failed, next probe at 09:46:04 set reset_at to 09:47:04, and so on) - producing an indefinite, silently-repeating false-positive '1 minute away from recovery' signal with no way for a human glancing at the DB or UI to tell the difference between a real short rate-limit and a login that needs manual re-authentication. Scope: distinguish an authentication/login failure from a genuine capacity/rate-limit response by matching on the actual error text ('Failed to authenticate', 'OAuth session expired', or similar) rather than defaulting every unparseable non-zero exit to the same exhausted-with-1-minute-retry bucket; surface an auth failure as its own distinct provider_status value (e.g. 'auth_required') with a message that tells a human to run claude login rather than implying the system will recover on its own; and make that state visible somewhere a human will actually see it - the worker log alone was not enough, since this went unnoticed until a specific dispatch was manually chased down. Also worth checking whether isProviderAvailable's own reset-time-passed branch (line 3713, 'in-memory: provider reset time passed, marking available') then immediately re-triggers another failing real dispatch attempt each cycle, burning a claim/spawn attempt every time it optimistically believes recovery happened.
