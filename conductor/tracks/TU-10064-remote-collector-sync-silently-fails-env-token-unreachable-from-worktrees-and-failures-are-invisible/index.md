# Track TU-10064: Remote collector sync silently fails: .env token unreachable from worktrees, and failures are invisible

**Problem**: The worker is the only component that writes to remote collectors, but every remote write has been failing with 401 and nothing surfaces it. Confirmed live 2026-09-04: 560 occurrences of [collector-1] write failed: 401 {error: unauthorized: missing token} in conductor/.sync.log, against 15696 total remote request attempts. The cloud has been receiving nothing while localhost worked fine, and no human-visible signal existed anywhere. Ownership, for the record, because it is genuinely ambiguous in the current design: the WORKER owns remote sync, not the API. postCollectors and patchCollectors in conductor/laneconductor.sync.mjs (around lines 940 and 967) are the only fan-out point in the system: collector[0] is awaited and its result returned, while collectors[1..n] are fire-and-forget with only a .catch that console.warns. The local API server ui/server/index.mjs does NOT write to the cloud at all: its collectorWrite helper posts to COLLECTOR_URL which defaults to http://127.0.0.1:8091, i.e. itself (line 46). It does hold a CLOUD_FUNCTIONS_URL constant (line 128) but that is only used to proxy READS in production, which makes it look cloud-responsible for writes when it is not. Root cause of the 401s: the token lives in .env as COLLECTOR_1_TOKEN and is present and well-formed (40 chars, lc_ prefix). The worker loads it at laneconductor.sync.mjs line 297 with existsSync('.env'), a RELATIVE path resolved against process.cwd(). .env is gitignored (.gitignore line 7), so it exists only in the primary checkout and in none of the 12+ worktrees under .worktrees/. Any worker process whose cwd is inside a worktree therefore finds no .env, never sets COLLECTOR_1_TOKEN, resolveToken (line 908) returns null, post() (line 659) skips the Authorization header entirely because it is guarded by if (token), and the remote correctly answers 401 unauthorized: missing token. Worker processes spawned from inside worktrees are not hypothetical: the comment at laneconductor.sync.mjs line 8407 (track 10044) already documents that worker processes spawned from inside a track's own worktree register with the real production collector and can pull real dispatch entries, and several such processes were observed running during this session, some at 100 percent CPU for hours. The error text is worth emphasizing because it points at the mechanism precisely: the remote says missing token, not invalid token, meaning no Authorization header arrived rather than a bad credential. Two things to fix, and they are separable. First, the narrow bug: resolve .env from the primary repo root rather than from cwd. resolvePrimaryRepoRoot() already exists in this same file and is used for exactly this class of cwd-dependence bug at the dispatch path (line 8422) and elsewhere; note the .env load happens very early at line 297, so confirm the helper is available at that point or hoist accordingly. Second, and more important because it is what let this hide: remote write failure is completely invisible. There is no retry, no queue, no per-track synced-to-remote state, no UI surface, and no aggregate counter. 560 consecutive failures produced nothing a human would ever see short of grepping the raw worker log. Consider a per-track remote-sync status, a retry queue for failed remote writes, or at minimum a periodic aggregate warning plus a visible indicator in the UI when a configured remote collector has been failing. Worth deciding explicitly whether a remote collector failing should be treated as degraded-but-acceptable (current de facto behavior, since collector[0] still succeeds and the awaited result comes from it) or as something that must be surfaced loudly. Related: track 10061 covers the absence of any version or capability handshake between worker and collector, which is the same category of silent-drift problem; this one is about silent AUTH failure and silent write loss rather than silent contract drift. Also note the naming confusion is itself part of the problem and may be worth addressing in docs: the local API server is called a collector, the remote endpoint is called a collector, and the API server holds a cloud URL, so a reader cannot tell from the code which component is responsible for getting data to app.laneconductor.com.
