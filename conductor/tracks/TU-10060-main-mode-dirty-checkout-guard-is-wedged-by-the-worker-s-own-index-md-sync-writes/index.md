**Problem**: The main-mode pre-spawn guard (conductor/laneconductor.sync.mjs around line 4894) refuses to spawn a main-mode lane action when the primary checkout has uncommitted changes outside the track's own folder. The done lane's merge action is forced to workspace main, so this guard gates every merge in the project. The problem is that the worker itself is the main producer of that dirt: it writes Lane, Lane Status, Progress and related status markers into conductor/tracks/*/index.md in the PRIMARY checkout on its normal sync cycle, for tracks unrelated to the one trying to spawn. The worker therefore creates the exact condition that blocks it, then reports it to the human as an external problem to clean up. Observed live 2026-09-03 on track 10051, sitting at done:queue with the message 'Main-mode run blocked - the primary checkout has unrelated uncommitted changes outside this track's folder: prisma/schema.sql'. After committing prisma/schema.sql and the accumulated track marker churn, the working tree was fully clean; within roughly two minutes the worker had modified conductor/tracks/TU-10055-.../index.md again with no human involvement, restoring the blocking condition. A human can only ever win this race by accident. Confirmed a second time the same evening: an auto-complete-track dispatch for 10051 (id 3146) fired on its own at 22:56:26, right after a clean-tree commit, and failed with 'done spawn blocked (warn)' for the identical reason — auto-complete chains are not gated by --sync-only the way new-queue claiming is, so they retry into the same wedge repeatedly. The guard itself is correct and should stay. The documented reason it exists is real: a main-mode session operating on a dirty tree sweeps unrelated pending work into its own commits, which happened the same day when a live merge session for track 10016 absorbed unrelated staged edits. What is wrong is the dirt classification. An index.md status marker written by the worker is not unrelated human work at risk of being clobbered, it is the worker's own bookkeeping. There is already an auto_heal path around line 4863 but it is opt-in via manager.auto_heal and only covers ignored build output, so it does not apply. Options worth weighing during planning: teach the guard to ignore or auto-commit worker-authored status-marker-only diffs to conductor/tracks/*/index.md, distinguishing a marker-only change from a real body edit; or stop writing markers into the primary checkout's working tree at all and keep that state solely in the database plus worktrees; or extend auto_heal to cover this class and enable it by default for marker-only diffs. Also confirm whether prisma/schema.sql drifting is a recurring generated-file problem or was a one-off from the track 10053 migration. Impact is at least two blocked tracks so far (10051 twice), and the failure mode reads as a human housekeeping problem rather than a bug, which is why it went unnoticed.
