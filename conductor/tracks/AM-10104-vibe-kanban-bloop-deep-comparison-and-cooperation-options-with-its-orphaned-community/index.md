**Problem**: Continue the LaneConductor vs Vibe Kanban comparison started 2026-09-20 and evaluate cooperation. Facts gathered live from github.com/BloopAI/vibe-kanban and vibekanban.com: Bloop announced Vibe Kanban is sunsetting (April 2026) -- paid cloud and remote services sunset, project continues as community-maintained Apache-2.0 open source; 28.1k stars, 3.0k forks, 385 open issues, 2080 commits; Rust backend + TypeScript frontend, SQLx DB, npx vibe-kanban install, Docker/self-host, hybrid local desktop + cloud instances; supports 10+ agents (Claude Code, Gemini CLI, GitHub Copilot, Codex, Cursor, Amp, OpenCode, Droid, CCR, Qwen Code); features: kanban with parent/sub-issues, git worktree per task, inline diff code review with comments, built-in browser preview with device emulation, PR creation with AI-generated descriptions, MCP integration, remote SSH editor (VS Code), multi-origin reverse-proxy support, team issue tracking with status auto-updated from PR merges. Positioning: 'accelerate the human planning and review your coding agents are waiting on' -- a single-developer, single-stage (plan -> prompt -> review -> PR) framing. Where it is ahead of LaneConductor: review UX (inline line-level diff comments), browser preview, one-line install, agent breadth via a normalized adapter, PR descriptions. Where LaneConductor is structurally ahead: multi-lane gated pipeline (plan/implement/review/quality-gate/done) with self-failing review, worker fleet across machines (identity, visibility, claim scoping, manager worker) with hub/federation/quota/run-ledger on the roadmap, markdown-in-git track docs as source of truth (works skill-only without a DB), App Creator wizard generating tracks plus a gated deploy track, non-dev tracks measured against KPIs, sovereign/marketplace distribution (AM-10098). Strategic read: 28k stars did not make a business of the board layer alone, which supports keeping ledger/hub ahead of polish; its community is now orphaned and used to agent-agnostic worktree kanban. Scope for this track: (1) finish a feature-by-feature comparison against the actual VK code/UX, not just marketing pages; (2) identify what to borrow (inline diff review, browser preview, npx-style install, agent adapter layer, PR description generation) and estimate effort; (3) evaluate cooperation options with the orphaned community: import/compatibility for VK tasks and workspaces, reusing Apache-2.0 components inside an ELv2 project (confirm license compatibility and attribution requirements), contributing upstream or maintaining a fork of specific pieces, outreach to the maintainers, and positioning LaneConductor as a landing place; (4) recommend a sequence relative to the v1.5 roadmap, with the constraint that any community landing depends on the reliability baseline AM-10099 established. Deliverables are documents and a recommendation, not code.
