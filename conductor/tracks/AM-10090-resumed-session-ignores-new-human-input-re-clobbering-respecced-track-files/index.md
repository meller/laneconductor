**Problem**: A resumed lane-action session (FRESH_SESSION: false) can act on stale in-context state instead of re-reading conversation.md for new human input, and overwrite files a human just edited. Reproduced live in the livingwork project on track AM-1020: the track was originally created by accident via a leaked lc new --help CLI arg (title literally '--help', no description). A plan run correctly diagnosed this as bogus, wrote a disciplined blocked spec.md/plan.md/test.md, set Auto Run to no, and asked the human to choose delete-vs-respecify. The human replied with a real respecification request ('i want a foggian track - as 1020 - if needed replan respac retest'). A fresh planning pass correctly rewrote spec.md/plan.md/test.md/index.md with real, code-grounded requirements and moved the track to implement:queue with Auto Run yes. Over the following several minutes, the automatic worker (mode sync+poll) repeatedly re-dispatched what appears to be the SAME earlier session (same session id, e.g. b744095c..., invoked with FRESH_SESSION: false each time) for track 1020. That resumed session's own in-context understanding was still the pre-respec 'no requirements, blocked' conclusion from before the human's message existed in its context. Each time it ran, it wrote spec.md and plan.md back to that old content (index.md's Problem/Solution/Phases prose survived because those aren't part of the marker-patch mechanism, but Summary/Phase/Waiting-Reason markers and both full spec.md/plan.md files were fully overwritten). This happened at least 3 times within about 10 minutes, each manual restore immediately re-clobbered by the next automatic dispatch of the same stale session. The only way found to stop it was setting Auto Run to no on the track, which prevents the automatic worker from claiming it at all. Root cause hypothesis: the session-resumption mechanism (Protocol: Session Continuity in the skill) resumes the literal prior Claude conversation state keyed by (worker, track) without checking whether new turns (a human reply, or a completely new planning pass by a different session) have landed in conversation.md/spec.md/plan.md since that session was last active. The skill's own instructions say a resumed session should still read conversation.md for new human input even when FRESH_SESSION is false, but in this case the dispatch apparently never gave that resumed session a chance to notice its own files had changed underneath it — it just re-asserted its cached conclusion. Impact: any track that gets replanned or edited by a human/another session while an earlier session for that same track is still resumable is at risk of having that work silently discarded by the next automatic dispatch, with no error or warning — this is a real data-loss footgun for exactly the kind of human correction/respec workflow the skill explicitly documents as supported (see the skill's Protocol: Session Continuity notes about a human comment landing since the last turn). Suggested directions to investigate: (1) before a resumed session's dispatch prompt runs, diff the track's current file mtimes/content-hashes against what that session last wrote, and force FRESH_SESSION: true (or otherwise force a re-read) if anything changed out from under it; (2) never resume a session whose last known conclusion was a blocked/backlog park if the track's Lane/Auto-Run marker state now differs from what that session set, since that mismatch is itself evidence of an out-of-band change; (3) at minimum, have the resumed session's own dispatch prompt explicitly include a diff or fresh copy of conversation.md/spec.md/plan.md rather than relying on the model to decide to re-read them.
**Summary**: Root cause confirmed in code: resolveTrackSession() decides resume-vs-fresh from context size and resume count only, spawnCli skips all context injection on resume, and track 10020's unanswered-human-tail signal is empty precisely when another session already answered the human. Fix: record a digest of the track's authored documents on the session row and refuse to resume when it no longer matches. 6 phases planned.
