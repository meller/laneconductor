**Problem**: ui/server/index.mjs's syncTrackToFile() (line 1550) resolves which folder to write into with its own inline regex: trackDirs = readdirSync(tracksDir).filter(d => d.match(/^(\d+)-/) && match[1] === trackNum.toString()). This picks whichever folder happens to start with the bare numeric track number, with no tie-breaking when more than one exists, and no use of the same ambiguous-folder-quarantine resolution the rest of the codebase already has (resolveTrackFolder, used by the sync worker and elsewhere). A track routinely ends up with two or three folders for the same track number: the canonical one lc new creates (author-prefixed, e.g. TU-10062-slug), a bare numeric one the worktree-artifact-merge path creates when a planning agent creates its own track dir inside the worktree and the primary checkout has no matching folder yet (worktree-artifact-merge.mjs's own comment documents this: copy whole dir to main), and sometimes a _duplicate-NNNN-slug quarantine copy on top. Confirmed live 2026-09-04: PATCH /api/projects/:id/tracks/:num/auto-run correctly updated tracks.auto_run in the DB, but the **Auto Run** marker landed in conductor/tracks/10062-claude-capacity-probe-.../index.md (the bare numeric folder), not conductor/tracks/TU-10062-claude-capacity-probe-.../index.md (the canonical one the UI's own Overview tab and every other check in this project reads from) - so the toggle appeared to silently do nothing from the human's side, reported live as 'is this a UI bug - I tried auto run on'. Worse than a one-off wrong write: a follow-up direct PATCH via curl set auto_run=true in the DB and confirmed it immediately after, but a later read showed auto_run back to false with no human action in between - consistent with some other sync path (the worker's own file->DB push, likely using a DIFFERENT folder-resolution than syncTrackToFile's) reading the untouched canonical folder as authoritative and pushing its absent Auto Run marker back over the DB value, undoing the PATCH. That means at least two independent parts of this codebase disagree about which folder is canonical for the same track, and can fight each other's writes. Scope: make syncTrackToFile() use the same resolveTrackFolder()/ambiguous-folder resolution logic the sync worker already has, instead of its own bare regex, so every PATCH-triggered marker write (lane_status, progress_percent, auto_run, merge_mode, waiting_reason - everything this function touches, not just Auto Run) lands in the one folder every other part of the system treats as canonical. Also worth a periodic or on-write check that logs or flags when a track has more than one matching folder, since that state is silently tolerated everywhere right now and is clearly common - it was already present on 10051 (four folder variants) and immediately reappeared on all four freshly created tracks 10059-10062 within minutes of creation, seemingly generated by the normal plan-lane worktree flow itself, not by anything unusual.
**Summary**: Root cause confirmed live: syncTrackToFile's own folder-missing recreate branch (bare ^(\d+)- regex) is blind to prefixed INITIALS-NNN-slug folders, so it recreates a bare-numeric duplicate from DB content, writes every marker into it, and the worker then quarantines that folder and pushes the marker-less canonical state back over the DB - the flap. Four more API call sites share the same legacy-only scan, and lc track-dir disagrees with the worker on the tie-break. Fix: one shared read-only resolver (track-folder-fs.mjs) used by the worker, the CLI and all five server call sites, plus duplicate-folder warn logging and lc track-dir --audit. 5 phases.
